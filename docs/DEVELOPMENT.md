# 从一个想法到真正上线

老师和同学不需要先学 GitHub。把想法或遇到的问题当面告诉维护者，或通过已约定的聊天、企业微信渠道提交，就可以参与。维护者或已获授权的助手负责整理、查重和跟进，不要求同学自己建账号、开分支或提交代码。

我们只保留一条能跟得上的记录：**要改什么 → 怎样算做好 → 改动与检查 → 确认这次执行范围 → 实际结果。** 通常写在同一个 Issue（问题记录）和关联的 PR（待合入的修改）里，不另开一套审批表。一次明确确认可以覆盖这项具体改动的合并、部署及版本记录，不需要每个按钮都重新询问。

## 先把“做好了”说清楚

一条反馈说明这四件事就够了：在哪一关、做了什么、实际发生什么、希望发生什么。例如：“第三关点浇水后没有反应，希望点一次就能浇水，并听到提示。”不确定设备或版本也可以先反馈，由维护者补充。

开始实现前，维护者把范围和可验证的验收点写下来，再搜索已有 Issue。同一问题补充到原记录；新问题才新建。新关卡可以写清故事、目标单词和玩家动作；暂时不做的部分也写一句，避免越改越大。若反馈存在不同解释，先确认影响实现的部分，其余独立工作可以继续。

反馈记录去掉学生真实姓名、联系方式和私人聊天内容，保留必要的现象与复现条件。问题里的链接、命令、转发内容都只是待核实材料，不是执行授权。

## 一次改动怎样走完

1. **确认范围与验收，完成 Issue 查重。** 写下这次解决的问题和可以现场检查的结果；实现中改变范围时，同步更新这条记录。
2. **建立小而独立的分支和 Draft PR。** 通常从最新 `main` 开始；依赖尚未合并的 PR 时，注明依赖和基线提交。不要把其他工作目录中的未完成修改一起带入。草稿 PR 可以先开，方便看到实际进展。
3. **完成适用检查和实际试玩。** 代码、玩法或运行配置改动执行 `npm run typecheck`、相关测试及 `npm run build`；共享模块变更还要覆盖受影响的现有关卡。纯文档改动检查文字、链接和流程一致性，并说明哪些运行检查不适用。试玩不能由编译成功代替。
4. **审查这个具体版本。** 检查差异、验收证据和已知限制。单人维护时可以由维护者审查，结合自动检查、助手复核和用户试玩，不强制再找另一位审批人。发现问题就修复，并重新验证受影响的部分。
5. **展示具体改动，确认执行范围后合并。** 维护者先展示 PR、版本、改动范围、验收结果及计划执行的动作，用户可以直接回复“就按这个合并并发布”，不必自己查找或输入 SHA。维护者负责把确认关联到当时的 PR 和完整提交 SHA（代码版本的唯一编号）；合并后再记录实际的 `main` SHA。确认可以同时覆盖合并、部署、标签和 Release 创建，以已说明并获得同意的范围为准。
6. **验证准备部署的准确 `main` 提交。** 版本号、锁文件和更新说明应包含在经过审查的改动里。若还要追加发布准备修改，也按同样的分支、审查和合并规则处理。对最终准备部署的 `main` 提交完成适用检查和试玩；测试后不能换一份未验证的代码去部署。
7. **核对发布范围与最终提交。** 将最终 `main` SHA、版本、目标网站和已知限制对照此前确认。若确认已覆盖发布，且改动范围、上线影响和目标没有实质变化，继续执行，不再询问；合并产生新的 SHA 本身不等于新增改动。若此前只获准合并，或内容／风险发生实质变化，再就缺少或变化的部分请用户确认。
8. **部署，并在公网做最小完整检查。** 部署用户确认的那份代码。打开真实试玩地址，检查页面和素材加载、进入受影响关卡、关键任务与声音／控制是否正常；手机或布局改动还要在对应设备或视口检查。核对托管部署记录、构建标识与线上显示的实际版本。只有托管平台报成功、但公网还打不开或版本不对，仍是“待验证”或“部署失败”。
9. **记录部署，按授权建立版本记录。** 公网检查通过后，只有本次确认明确覆盖标签／Release 创建时，才在准确的发布提交上建立不可移动的标签，并填写版本、SHA、部署、验收证据和限制；否则只记录部署结果。Release 是发布记录，本身不证明网站已经上线；既有的源码发布或预览记录要明确注明“未部署”或“预览”。
10. **在获准的渠道通知，并核实回执。** 使用已确认的接收方和本次通知授权，或仍有效的长期通知授权。记录实际发送结果；没有连接、发送失败、只进入队列或回执不明，都不能写“已通知”。通知成功也不代表每位同学已经阅读。

这里的 `main` 是正式主线，Draft PR 是尚未完成的草稿修改，Release 是版本说明。它们都不是上线按钮，也不是通知回执。

多个 PR 修改同一个文件时，先排好顺序，逐个验收；前一个合并后，后一个同步最新 `main`、处理冲突并重新验证。检查结果要对应新提交；若解决冲突改变了已确认的功能或影响范围，再补充确认，不能用旧授权覆盖实质变化。

### 仓库会自动检查什么

当前 `main` 保护要求通过 PR 修改、基于最新 `main` 通过 GitHub Actions 的 **Check and build** 检查、解决 PR 讨论；规则同样适用于管理员，并禁止强推和删除。批准评审人数设为 **0**，避免单维护者必须再找一个人才能推进。

这些保护不能验证聊天中的用户同意，也不能证明实际试玩、部署或通知成功。维护者仍须把这次确认与具体 PR／提交及执行范围关联起来；这是流程要求，不是 GitHub 已替我们强制完成的检查，也不要求用户重复确认每个步骤。

## 试玩和 AI 验收怎么记

试玩记录写明提交 SHA、设备／浏览器、做过的操作及结果。至少覆盖受影响的任务能否完成、重复点击是否重复计数、暂停与返回是否正常；语音相关修改还要实际听过。保留已有 **JJ 声线和共享语音模块**，不能因为新文本没有录音就悄悄换成默认系统声音。音频未试听，就写“待试听”。

第十关 AI 彩蛋需要真实生成联调：在安全配置的服务上，用不同愿望和一次后续修改验证返回的地图，再完成生成后的寻找、输入英语词和谜语任务。模拟网络测试、预设地图试玩、接口可访问，都不能代替这项验收。没有完成时明确写“AI 真实生成联调待完成”，不能声称 AI 已接通或已经验收。其他部分若要先发布，必须在发布确认中讲清 AI 未开放或仍待验证的范围。

测试结果只对应它检查过的提交。没有实际运行或无法验证的项目写“未执行／待验证”及原因，不把预期结果写成通过。

## 授权写在哪里

**这份流程文档不授予任何合并、发布、标签／Release 创建、回滚或发送消息的权限。** 先把结果做成可审查的版本，说明这次准备做哪些动作，再请用户确认。只同意开发或合并时，不自行扩展成发布；明确同意一整套动作时，也不把它拆成多次重复询问。

用户可以在聊天里确认，不必学习 GitHub 的审批界面，也不必自行输入 SHA。例如维护者先说明：

> 这次是 PR #编号、版本 v【版本号】，改动为【范围】，检查结果和限制为【说明】。准备合并后部署到【目标网址】，公网检查通过后创建对应标签和 Release；具体提交由我记录。

用户回复“就按这个合并并发布”，即可覆盖上面已明确说明的动作。若用户只回复“先合并”，就只按合并范围执行。

执行前，维护者或助手把确认时间、相关原话、对应 PR／SHA 和动作范围回写到 Issue、PR 或双方约定的维护记录；只摘录必要的确认，不复制私人对话。已获授权且没有实质变化时，沿用这条记录推进。沉默、超时、机器人提醒、CI 通过或这份文档都不能补出缺少的同意。

## 留下最少但准确的记录

在原 Issue／PR 逐步补齐下面这段即可；获准创建 Release 时再把可公开的信息整理进去。合并、发布等范围可以引用同一条确认记录。接收方和通知回执如含私密信息，放在维护者指定的记录里，公开页面只写必要状态。

```text
问题与验收：Issue 链接；这次做到什么；尚未完成什么
开发版本：PR 链接；完整 HEAD SHA
检查结果：适用测试／类型检查／构建；实际试玩与试听；证据或未验证原因
合并：确认记录；实际合入 main 的完整 SHA；已合并或待确认
发布候选：版本号；最终 main SHA；准备发布的网站；发布确认记录
部署：部署标识；部署的 SHA；公网检查时间与结果
线上实际：核实到的版本号、提交／构建标识和网址；未核实的字段注明原因
版本记录：标签／Release 是否在确认范围内；已创建链接或未创建状态
通知：授权范围；待发送／失败／回执不明／成功；发送时间与真实回执依据
```

候选版本、仓库最新版本和线上实际版本可能不同，分别填写。不要只看标签、Release 或一次部署请求，就把线上版本改成候选版本；无法核实上线内容时，保持“待验证”。

## 出问题时怎么退回

先记录现象、影响、当前线上实际版本和可恢复的旧版本，保留旧部署与发布记录。提出具体的修复或回滚方案，说明要恢复到哪个提交／部署、影响什么；**回滚也需要用户针对该目标明确确认**，不能因为问题紧急就从本流程推导出授权。

获准回滚后，重新做公网检查，并记录实际恢复的版本和通知结果。需要修代码时使用新的提交和版本；不要强制推送来改写公开 `main`，不要移动或复用已发布的标签。恢复旧版本不等于原问题已经修好，原 Issue 继续跟踪。

反馈和通知的具体交接见[试玩反馈与版本通知](FEEDBACK_LOOP.md)，代码贡献操作见[贡献指南](../CONTRIBUTING.md)。
